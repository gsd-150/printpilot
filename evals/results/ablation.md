# 消融报告 — dev 与 holdout，含配对检验

- **日期**：2026-07-30
- **模型**：`claude-sonnet-4-5-20250929`（日期锁定，全部 LLM 档一致）
- **提示词**：`diagnosis/v1_baseline`（两个 LLM 档共用同一文件，唯一变量是 Skills 注入）
- **数据**：`master_seed=42`，`scenario_version=1.0.0`
- **逐案例结果**：`evals/runs/*.json`
- **复现**：

```bash
uv run printpilot eval --split holdout --diagnoser llm+skills --workers 8 --save holdout-skills
```

区间为 bootstrap 百分位区间（2000 次重采样，95%）；配对比较为 McNemar 精确二项检验。

## 一、规则基线严格支配，且没有一条反例

两个划分上，**LLM 没有答对过任何一条规则基线答错的案例**。dev 25:0，holdout 8:0。

这比准确率差距更强：它意味着 LLM 在本任务上不仅更差，而且**不提供任何互补覆盖**。
没有"规则漏掉但模型能捕捉"的场景，一个也没有。

原因是任务结构决定的。判别依据是少数几个连续特征的阈值与符号——流量是否持续偏低、
电流朝哪个方向变、温度是否越窗。这类判断可以被精确写下来，交给概率系统只是把
确定性换成了不确定性，还附带成本与延迟。

**这正是本项目把感知层与执行层留在 Python、只让 LLM 承担开放式推理的理由。**
架构判断先于实验作出，实验现在给了它一个数字。

## 二、Skills 有效，在 holdout 上复现，且机制可追溯

`llm` → `llm+skills`：dev p=0.0003，holdout p=0.0078，**holdout 上 8:0 无反例**。
在门禁划分上复现，不是 dev 上的过拟合。

逐案例混淆矩阵显示修复发生在预测的位置：

| 主要错误 | llm | llm+skills |
|---|---:|---:|
| `UNDEREXT_PARAM` → `CLOG_PARTIAL` | **20 / 20 全错** | 2 |
| `THERMAL_DRIFT` → `CLOG_PARTIAL` | 15 | 6 |

M4 的定性判断是「模型过度预测部分堵塞，因为不掌握『挤出机电流正常即无机械阻力』
这条事实」。Skill 注入的正是这条事实，被修复的正是这两个类别。

对照 v2 提示词的纯结构性改动（强制多假设、禁止解释掉证据、可判定的弃权条件）
在 20 条上只多答对 1 条。**知识差距无法用推理纪律补上**——该假设在 M4 被证伪，
在此被正面证实。

## 三、最严重的发现：LLM 档在 holdout 上把 10% 的堵塞送进了参数路径

| 划分 | rules | llm | llm+skills |
|---|---|---|---|
| dev | 0.000 | 0.000 | 0.010 |
| holdout | 0.000 | 0.000 | **0.100** |

holdout 30 条中有 3 条堵塞被判为参数路径可接受的类别。在真实设备上，这意味着
**向受阻的喷嘴增大流量**——挤出压力上升、驱动齿轮磨削料丝，一个可修的故障变成一次拆机。

两个 LLM 档的 `CLOG_FULL` 召回在 holdout 上均为 **0.000**（6/6 全部漏判），
dev 上分别为 0.450 与 0.200。这个类别在 dev 上就弱，离开 dev 后彻底失效。

需要说明的是 `llm` 档 0.000 的误路由率是**退化解**：它把 25/30 判成部分堵塞，
堵塞自然永不进参数路径。Skills 压下过度预测后，真实误判暴露出来。

**这条结果直接验证了 SafetyGate（M7）的必要性。** 模型不能被信任来正确路由堵塞，
所以动作层必须有一道纯 Python 的硬拦截，而不是依赖模型不犯错。在那之前，
本系统的 LLM 档不应被用于任何会触及设备的场景。

## 四、LLM 档的泛化更差

| | dev → holdout |
|---|---|
| rules | 0.960 → 0.933（−0.027） |
| llm | 0.510 → 0.400（−0.110） |
| llm+skills | 0.710 → 0.667（−0.043） |

规则几乎不掉分。holdout 与 dev 的差异仅在材料/几何组合，而规则依据的是物理耦合方向，
本就不随这些因素变化。

## 五、成本

| | llm | llm+skills | 倍数 |
|---|---:|---:|---:|
| token/案例（holdout） | 3,811 | 6,721 | 1.76× |
| 全量 dev 耗时（8 路并发） | 205s | 260s | — |
| 规则基线 | 0 token | 0 token | <1s |

`llm+skills` 相对 `llm` 的 +0.20 准确率，代价是 1.76 倍 token；而两者都不及
一个零成本、亚秒级的规则实现。

## 六、已知局限

- **challenge 划分尚未运行 LLM 档。** 那 30 条包含未见材料、超范围噪声与移除
  判别信号的案例，是弃权机制真正被检验的地方。本报告不覆盖。
- **数据为合成。** 仿真器的故障 signature 虽有重叠设计，仍比真实产线干净，
  全部指标存在上界。规则基线的优势在真实数据上大概率会收窄——真实信号更脏、
  边界更模糊，而这正是 LLM 可能开始有价值的地方。**本报告不支持"LLM 在此类任务上
  总是更差"这一更强的结论。**
- **温度为 0 但供应商不保证确定性**，重跑可能有小幅波动。
- **Skill 内容有待改进**：`CLOG_FULL` 的召回退化可从 `extrusion-anomaly-triage`
  的内容读出——判别表大量篇幅给了堵塞与参数的对比，完全堵塞只在流程第 1 步一笔带过。
  记为 v0.2.0 待办。
