# 检索评测报告

- **日期**：2026-07-30
- **语料**：12 张知识卡片（`knowledge/accepted/`），语义切分——**一张卡 = 一个 chunk**
- **评测集**：35 条查询（`evals/retrieval_qa.jsonl`），含同义改写与多正确答案
- **向量库**：ChromaDB 1.5.9，余弦距离
- **复现**：

```bash
uv run printpilot rag eval
```

---

## 结果

| Embedder | 语义 | Hit@1 | Hit@3 | Hit@5 | MRR |
|---|---|---|---|---|---|
| `text-embedding-3-small`（1536 维） | 是 | **0.800** | **0.943** | **1.000** | **0.878** |
| `deterministic-trigram-256` | **否** | 0.200 | 0.514 | 0.686 | 0.370 |

第二行**不是一个可引用的结果**。它是一个哈希三元组袋，只按字面重叠匹配，
存在的唯一目的是让 store、元数据过滤与排序链路能在无 API key 的条件下被测试——
这是验收要求。把它列在这里是为了给出一个"完全没有语义能力时长什么样"的下界：
Hit@1 0.200 对应 12 选 1 的随机猜测（0.083）略好一点，因为字面重叠仍有微弱信号。

## 为什么同时报 Hit@k 和 MRR

两者的失效方式不同。Hit@3 说"正确卡片在窗口内"，MRR 说"它是不是第一条"。

一个稳定把答案排在第三位的检索器，实际比 Hit@3 单看起来更差——排在它上面的
都是模型必须读过去的上下文，既占预算又稀释注意力。本次 Hit@1 0.800 与 MRR 0.878
接近，说明命中时大多排在首位，而不是勉强挤进窗口。

## 语料与切分

**一张卡 = 一个 chunk**，不再二次切分。理由是这批内容本身就是按"一个可独立回答的
判断"组织的：把"用电流方向区分堵塞与参数故障"切成两半，任何一半都不再能回答
那个问题。固定窗口切分会切断表格和对照关系，在这种结构化语料上是明确更差的选择。

清洗流水线的实测：**12 进 → 12 出，未剔除任何卡片**。这不是"清洗没生效"——
规则（id 重复、正文过短、被取代、近重复）都有对应的单元测试证明会触发，
只是这批自撰语料本身没有触发条件。报告 12→12 比报告"已清洗"更有信息量。

## 元数据

每个 chunk 携带 `source_title` / `source_url` / `license` / `retrieved_at` /
`content_hash` / `applicable_material` / `evidence_level` / `supersedes`。

`content_hash` 使被引用段落的静默改动可被下游发现。
`applicable_material` 支持**先过滤再排序**——要三条结果时返回三条*适用*的，
而不是三条候选里挑剩几条。

## 局限

- **语料是自撰的，不是转录的。** 这些卡片基于公开 FDM 工艺常识由本项目撰写，
  `source_url` 一律留空而**不是填一个看起来合理的链接**——后者是伪造引用。
  真实系统需要有实际出处的材料，这一点记为局限而非掩盖。
  `tests/test_rag.py::test_no_fabricated_source_urls` 固化了这条约束。
- **12 条语料的规模下，向量库不是性能选择。** 同样的结果用一次暴力余弦扫描就能
  得到，而且更快。使用 ChromaDB 是为了接口——持久化、元数据过滤，以及一个在语料
  增长后形状不变的查询路径。**本报告的数字反映的是 embedding 与语料的质量，
  不是索引结构的质量。**
- **评测集由撰写语料的同一方编写**，存在"提问方式贴合语料措辞"的偏置。
  更严格的做法是让不了解语料的人提问。
- 未做切分策略的横向对比（固定窗口 vs 语义），因为在一张卡即一个判断的结构下，
  固定窗口切分会破坏卡片内部的对照表，比较意义不大。这是一个判断，不是遗漏。
