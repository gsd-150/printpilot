# ADR 0002 — 有界并发与运行成本核算

- **状态**：已接受
- **日期**：2026-07-29
- **验证环境**：ChatAnywhere 中转，`claude-sonnet-4-5-20250929`，dev 等距抽样 20 条

---

## 背景

真实 schema 单次调用约 20 秒。串行下 160 条约 53 分钟，五档消融接近一个工作日。
这个时长会让人不愿重跑评测——而"愿意重跑"正是评测框架存在的目的。

## 决策

线程池有界并发，默认 8 路，硬上限 32。不用 asyncio：工作全是 HTTP 等待，
OpenAI SDK 的同步客户端本身线程安全，改异步要重写客户端和所有调用方而吞吐量并无增益。

调用方依赖两条性质：

1. **结果按输入顺序返回**，与完成顺序无关。下游按位置把预测与案例对齐，
   乱序会静默地拿错标签打分。
2. **并发不改变结果**。每条案例是独立调用、温度为 0；共享的只有计数器。

## 实测

| 指标 | 值 |
|---|---|
| 加速比（8 路） | **6.1×**（实际 125.4s vs API 累计 770s） |
| 结果一致性 | 准确率与全部分类别指标与串行完全相同 |
| 全量 dev（100 条）预计 | 约 10 分钟（原 53 分钟） |

`test_concurrency_does_not_change_results` 在 CI 中以规则基线断言第 2 条性质。

## 线程安全

`OpenAICompatibleClient` 的计数器是读-改-写。8 路并发下 token 统计与违规计数会竞态，
**产生静默错误的成本数字——这比不统计更糟**。全部改动经 `_lock`；SDK 客户端的
惰性初始化用双检锁，确保并发首调只创建一个实例。

`usage.latency_ms` 是各 worker 累加的 API 时间，并发下**大于**实际墙钟时间。
它衡量做了多少工作，不是等了多久。加速比由二者之比给出。

## 一次被实测推翻的优化

严格 `json_schema` 模式下 schema 已随 `response_format` 发送，system 消息里再 dump
一遍看起来是纯浪费——约 2,700 输入 token/次。移除后实测（同一批 20 条）：

| | schema 在 prompt 中 | 移除后 |
|---|---|---|
| 调用次数 | 22 | 40 |
| token 总量 | 99,506 | **201,735** |
| schema 违规率 | 9.1% | **50.0%** |

**发一遍比不发更贵。** 移除后模型半数输出通不过校验，每次失败都要一轮修复重试，
调用与 token 双双翻倍。已回退，并将该约束固化为测试。

### 由此暴露的探针缺陷

`llm-check` 曾报告三种模式均"可用"。但它只验证了**一次调用能被解析**——
一个仅名义支持的模式同样能通过这个检查。

在本中转上 `json_schema` 被接受并转发，但**不被强制执行**。
「支持」与「强制」是两个问题，探针只回答了前一个。

后续改进方向：探针应对同一模式重复 N 次并报告违规率，而非单次成败。
在此之前，`PRINTPILOT_LLM_STRUCTURED_MODE` 的取值应理解为"可发送"，而非"可依赖"。

## 成本核算

Token、违规率与耗时与准确率并排报告。一个以四倍成本换取两个点准确率的配置
不显然是改进——这类权衡正是消融实验要回答的问题。

核算采用鸭子类型：任何带 `usage` / `call_count` / `schema_violations` 的对象都会被统计；
规则基线三者皆无，被如实报告为零成本。
